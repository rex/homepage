## Context

I was the only infrastructure engineer for about ten venues. Each venue ran a three-node
RKE2 cluster on a standalone virtualization host, and a central Rancher cluster managed all
of them. Two weeks earlier I had finished moving every venue off the cloud and onto those
on-prem clusters. That same week we cut the cloud fleet from 51 instances to 26, and kept two
venues' cloud clusters running as a safety net.

## What happened

At 1 a.m. I ran our node-maintenance Ansible playbook against every venue at once. It ran
`apt` with `name: "*"` and `state: latest`, plus an LVM expand, on every Ubuntu Kubernetes
node VM in parallel. It had no `serial:` and no drain. I'd tried it on a single node the
evening before. By morning, the venue clusters were down.

## What made it hard

- **Ten clusters broke at the same moment.** The Rancher management plane I'd normally
  recover them through was already degraded from the previous week, and the churn made it
  worse.
- **Nodes looked healthy** but wouldn't run containers, or even delete them.
- **I was the only person with the context to fix it,** and I was coming off a night of
  alerts.

## The narrowing

The VMs' IP addresses had all changed. The Kubernetes nodes were on DHCP with no
reservations, so when the upgrades restarted networking or rebooted them, they came back on
new addresses. RKE2 node registration, etcd peer URLs, Kong upstreams and DNS were all bound
to the old ones. That turned ten mysterious cluster failures into one cause.

## The decision I'd make differently

I chose to bring each cluster up on its new IPs and repoint everything at them, rather than
re-IP every VM, because that was faster per venue. It got the first four venues back, but too
slowly. Each venue looked one change away from coming up, and I stayed anchored on that.

At about 2:30 p.m. I remembered the two cloud clusters were still running. I repointed their
DNS and then rebuilt the rest of the cloud infrastructure as a fallback. Afterwards I was told
I should have pulled that trigger hours earlier, and that was right.

Why didn't I fail over sooner? Sunk cost, plus I didn't feel empowered to spend money on the
cloud again. Now I set the failover criteria before I start risky work, not during it.

## What changed

- **Static IPs for venue Kubernetes nodes,** on a fixed per-cluster scheme for every rebuilt
  cluster. I proposed it the next morning. My manager wisely froze changes for a day, and it
  went in with the rebuilds.
- **One venue per night.** I re-migrated venues one at a time instead of fleet-wide, and kept
  the cloud as a five-minute DNS fallback until it was fully retired about six weeks later.
- **Fresh nodes, not reused ones.** I rebuilt clusters on new nodes instead of cleaning and
  reusing broken ones. One venue's first rebuild failed for exactly that reason.
- **A clean management plane.** I removed obsolete RKE1 clusters from the Rancher management
  cluster, which had been pinning all three of its nodes at 100% CPU, and added monitoring on
  those nodes.

## What I'd do on the change itself

- Canary one venue first.
- Use `serial: 1`, and cordon and drain before touching a node.
- Run a preflight that asserts static addressing.
- Run it in the window when every venue is closed, with the fallback already armed.

The general rule: fleet-wide changes go canary first, then rolling. Never all at once.
